# CaptainPad 6969
**iPad Application Design & Architecture**

The CaptainPad is the primary control surface for the BM26-Titanic interactive LED installation. It bridges the gap between the MarsinEngine backend (pattern compilation & sACN routing) and the physical lights.

## 1. iPad Core UX / UI Principles

To follow best practices for iOS/iPadOS "Pro" applications (such as Logic Pro, LumaFusion, or professional lighting consoles like GrandMA):

1. **Navigation Rail (Left Sidebar):** Instead of a mobile-style bottom tab bar, iPad apps benefit greatly from a persistent left-side navigation rail. This maximizes vertical space for code editors and WebGL views.
2. **Split-Pane Architecture (Master-Detail):** Essential for an iPad. The left pane should contain lists (e.g., list of patterns, list of parameters), and the right pane should contain the active workspace (the code editor, the actual sliders).
3. **High-Tactility For Live Performance:** Button hit-boxes must be large. During a burn/event, it is dark and dusty; controls must be unambiguous. Accidental touches on critical buttons (like "Delete Pattern" or "Blackout") should require confirmation or be visually separated.
4. **Persistent System Status:** A thin bar at the top or bottom that always shows `Engine Status`, `FPS`, `Network Ping`, and `Active Scene`.

## 2. The Navigation Structure (Tabs)

### 🎛️ Tab 1: The Control Deck (Live Performance)
*The primary screen to be left open during the event.*
* **Left Pane (Pattern Queue):** A scrollable list of all available Pixelblaze patterns fetched from the server. Tapping one instantly sends a command to switch the engine's active pattern. The pattern list is **the active playlist for the deck's base channel**; there is no longer a "target channel" picker above it — see §2.x below.
* **Right Pane (Parameters & Macros):**
  * Dynamic sliders for the active pattern (Global Speed, Hue Shift, Intensity).
  * Quick-trigger Macro pads (e.g., "Trigger Burst", "Strobe").

#### Target channel removal (2026-05)

Earlier versions of the Control Deck rendered a **TARGET CHANNEL** pill
row above the playlist (`DECK MAIN` / `MIXER CH 1` / `MIXER CH 2` / …)
that let the operator preview a mixer channel's content from inside the
deck tab. That UX was removed in May 2026.

**Why:** the multi-channel workflow already lives in Tab 2's mixer
view; routing it into the deck via a second selector created two ways
to do the same thing and meant every deck control had to ask "am I
writing to the base channel or to a preview-only channel?". Playlists
already cover the "swap what's playing on the deck" use case
end-to-end, and PortWatch had the same picker as a view-only V1 stub
that operators reasonably expected to be tappable.

**What this means in practice:**

* The deck **always** targets the mixer base channel
  (`mixerChannels[0]`). The `setMixerView('deck', deckChannel?)`
  second argument is gone — `setMixerView('deck')` is all you get.
* The compact-status PUB wire payload shrank: the bridge no longer
  ships `tch` / `nch` / `chs` fields, and PortWatch no longer parses
  `targetChannelName` / `channelCount` / `channelNames`. See
  `docs/21_portwatch_monitor.md` §10.14 for the PortWatch side.
* Channel-level routing still lives in **Tab 2 (Dimmer Rack /
  Mixer)** — nothing about that flow changed.
* The engine endpoint `POST /mixer/view` still accepts
  `deckChannel` for backward compatibility (any other client that
  used to send it keeps working), but no first-party UI sends it
  any more.

### 🎚️ Tab 2: The Dimmer Rack (Global Section Control)
*For macroscopic intensity scaling across logical groups.*
* **Dynamic Generation:** Automatically builds `NauticalFader` sliders based on the `sectionId` metadata. This metadata is generated by the simulation's `auto_patcher.js` (which groups fixtures by their `group` name) and baked into the active model.
* **Independent Control:** Allows the operator to independently dim or boost specific physical fixture groups (e.g., `ParLights`, `BarLights`) relative to each other, without modifying the core pattern code.
* **Global Blackout:** A massive, highly-visible toggle that completely overrides all engine output.
* **Bypass Toggles:** Hardware-specific effect overrides (e.g., UV Blast Bypass).

### 💻 Tab 3: The Studio (Pattern Editor)
*For making adjustments and writing logic on the fly.*
* **Left Pane (File Explorer):** List of patterns (fetched via `GET /list-patterns`). Has an 'Add New' button.
* **Right Pane (Code Editor):** 
  * A `react-native-webview` encapsulating a `Monaco` code editor, or a robust React Native text area.
  * A floating **"Save & Compile"** button (`POST /save-pattern`) which pushes the code to the engine instantly to see the results.

### 👁️ Tab 4: The Monitor (Simulation Web Viewer)
*For visualizing the ship when away from the physical installation.*
* **Full Screen Layout:** Embeds the Three.js WebGL simulation using `react-native-webview`. 
* **Overlay Controls:** Transparent overlay buttons for "Refresh View" (in case the WebGL context drops) or viewing different camera angles defined in `cameras.yaml`.

### 🛠️ Tab 5: System Health & Swarm Data
*Crucial for Burning Man installations to diagnose hardware failures.*
* **Dashboard Widgets:**
  * **MarsinEngine Metrics:** Current FPS, memory usage, current sACN routing.
  * **Swarm Status:** A list tracking the status of all ESP32 controllers and SHEHDS fixtures based on data from `sacn_bridge.js`.
  * **Event Log:** A trailing console output showing realtime errors or connections (subscribes to `sacn_bridge` WebSockets).

### ⚙️ Tab 6: Settings & Config
* *Environment Variables:* Input fields to set the IP address of the `marsin_engine` server and `save_server`. 
* *Theme Toggle:* Toggle between Dark Mode (Stage Mode) and the "White Modern" designer aesthetic for daytime visibility.
* *DMX Patch Interface:* (Optional) Easy UI to modify `patches.yaml` dynamically if a controller breaks and needs to be swapped out on the playa.

## 4. Server Discovery & Connection Health

The CaptainPad must operate on unpredictable local networks (Burning Man, different WiFi setups, DHCP) where the MarsinEngine's IP address is not known in advance.

### 4.1 Server Identity Contract

MarsinEngine's `GET /status` endpoint returns a service identity marker:

```json
{
  "service": "marsin-engine",
  "name": "MarsinEngine",
  "version": "2.0",
  "port": 6968,
  "activeModel": "titanic",
  "activePattern": "rainbow",
  "activeScene": "titanic",
  "unrealState": "offline"
}
```

The `service` field prevents CaptainPad from accepting any random HTTP server on port 6968 during network scanning.

### 4.2 HTTP Subnet Scan (Primary Discovery)

CaptainPad discovers MarsinEngine instances via HTTP subnet scanning:

1. **Get device IP** via `expo-network` → `getIpAddressAsync()`
2. **Derive `/24` subnet** (e.g., `10.1.1.42` → `10.1.1.1..254`)
3. **Batch probe** each candidate IP on port 6968 with `GET /status` (400–800ms timeout, 24–40 concurrent)
4. **Filter** responses: only accept `service === "marsin-engine"`
5. **Display** discovered servers as tappable cards in Config tab

This approach requires no native mDNS dependencies, works on any network topology, and is compatible with Expo's managed workflow.

### 4.3 Connection Health

A shared connection-status context polls `/status` every 5 seconds and exposes:
- `isConnected` (boolean) — drives green/red sidebar indicator
- `latencyMs` — displayed in Config tab
- `serverInfo` — active pattern, model, scene
- `error` — surfaced in OFFLINE banners across all tabs

### 4.4 Manual Fallback

The Config tab retains a manual URL text input as a fallback for non-standard networks or when subnet scanning is impractical.

## 4.5 PortWatch / Deck Override (lock-out)

PortWatch (the field-ops iOS app, see `docs/21_portwatch_monitor.md`)
can take exclusive control of the deck from off-network — without
restarting the engine, and without any per-component awareness on
CaptainPad's side. CaptainPad listens for the lock state and disables
itself when an external owner is holding it.

### 4.5.1 The lock state

CaptainPad tracks a single value: `controlLock` (the canonical
`globalsState.controlLock` field on the engine). Two values today:

- `null` — nobody holds the lock; CaptainPad is fully interactive.
- `"portwatch"` — PortWatch holds the lock; CaptainPad is muted.

It hydrates from `GET /globals` on cold boot and follows live updates
via the engine's `viewOverride` WebSocket broadcast (and the future
`globals` broadcast — `useEngineLock` already listens for both).

### 4.5.2 The lockout overlay

`CaptainPad/components/EngineLockoutOverlay.tsx` is a single full-screen
overlay mounted in `app/(tabs)/_layout.tsx`. It:

- Uses `useEngineLock()` from `hooks/useEngineLock.ts` to read the
  current owner.
- Fades in (300 ms) when the lock is taken and fades out the moment it
  releases — no per-tab plumbing.
- Sets `pointerEvents="auto"` so it captures every gesture (taps,
  swipes, scrolls). The deck/mixer tab views below it remain fully
  rendered for visual context but cannot be interacted with.
- Sits at `zIndex: 900`, BELOW the persistent `ViewOverrideBanner` so
  the operator can still see who has the rig and dismiss banners.
- Renders a centered "EXTERNAL HAS THE RIG · PORTWATCH" message with
  a hint that release will land automatically when PortWatch clears
  the lock.

The overlay does **not** try to write to the engine when tapped — it
is strictly a coordination signal. The lock is enforced at the UX
layer; HTTP writes still succeed at the engine layer (any conflicts
between simultaneous writers are resolved by "last writer wins" plus
the next broadcast). The overlay's job is to make sure operators are
never *surprised* by a write conflict.

### 4.5.3 Wire path

PortWatch issues `cmd view/deck` → bridge calls
`POST /mixer/view-override {override: "deck"}` → engine sets
`viewOverrideMode = "deck"`, calls `syncControlLockToGlobals()`
(writes `globalsState.controlLock = "portwatch"` and persists), and
**arms a 30 s lease timer** → engine broadcasts `{type:
"viewOverride", override: "deck", controlLock: "portwatch",
controlLockLeaseExpiresAtMs: …, controlLockLeaseDurationMs: 30000}`
→ CaptainPad's `useEngineLock` fires → overlay raises within one
frame of the broadcast.

`cmd view/clear` is the same path with `controlLock` reverting to
`null` and the lease being disarmed; CaptainPad's overlay fades out
and the deck/mixer tabs are live again.

### 4.5.4 The lease (what CaptainPad inherits for free)

The override is a **lease**, not a permanent take. The engine fires a
30 s timer on every `POST /mixer/view-override {override: 'deck'}`
and auto-clears the lock when it expires. PortWatch keeps the lease
alive by sending `cmd view/renew` every ~20 s (silent — no toast, no
intent flip; just a wire CMD that resets the timer).

From CaptainPad's perspective this means:

* The overlay can lift **without anyone explicitly releasing** — if
  the PortWatch holding the lock walks out of range or its app
  crashes, the lease expires and the engine broadcasts the same
  `viewOverride` event with `override: null`. `useEngineLock()`
  reacts identically to a manual release; there's no separate "lease
  expired" code path to maintain.
* The overlay can render a soft "lease expires in Ns" hint by
  reading `controlLockLeaseExpiresAtMs` from the `viewOverride`
  broadcast, but we deliberately don't, today — the operator at
  CaptainPad doesn't need to think about it, the lease just
  *happens* and the overlay reflects ground truth.
* Boot-time hydration: if the engine restarted while the lock was
  held, `api_server.js` re-arms a fresh lease (it has no record of
  the previous expiry, so it conservatively gives the holder one
  full lease worth from boot). Without this a crash-and-restart
  during a held lock would strand CaptainPad indefinitely.

| Constant | Value | Defined in |
| -------- | ----- | ---------- |
| Lease duration | 30 s | `CONTROL_LOCK_LEASE_MS` in `marsin_engine/lib/api_server.js` |
| Renew interval (PortWatch) | 20 s | `LEASE_RENEW_INTERVAL_MS` in `control_podium/PortWatch/src/ui/DeckScreen.tsx` |

End-to-end tests: see `control_podium/tests/test_comms_e2e_sim.py`
(`test_lock_lease_auto_expires`, `test_view_renew_is_idempotent_take`).

### 4.5.5 What CaptainPad still does while locked

- Read-only display: the deck and mixer tab UIs render normally so
  the operator can see the current state of the rig.
- Live broadcasts continue to flow through `engineEvents` and update
  the displayed values; only writes are gated.
- The Studio tab (code editor) is also covered by the overlay — even
  saving a pattern during a live moment goes through the engine and
  affects what PortWatch is operating on, so it has to be blocked too.

## 4.6 The Centralised Engine State Hook

Adding "react to live engine state" to a new CaptainPad component is a
one-liner now. Previously every consumer (CPCControls, GlobalParams,
PlaylistPanel, etc.) bound `wsRef.current.addEventListener('message',
…)` inside its own `useEffect`, which:

1. Returned early at mount because `wsRef.current` was still `null` when
   the WS hadn't connected yet, and
2. Stayed bound to the dead WebSocket after the auto-reconnect loop
   replaced the instance — silently stopping fresh updates.

Both surfaces (CPC global params from PortWatch, local pattern exports
from PortWatch) hit those bugs and looked like "engine isn't
broadcasting", which was wrong — the engine broadcasts fine. The fix:

```ts
// hooks/useEngineState.ts
const { sharedParams, mixerChannels, blackout } = useEngineState();
const params = useSharedParamValues(defaults);
const exports = useChannelExports(channelId);
```

The hook lives at `CaptainPad/hooks/useEngineState.ts`. It subscribes
ONCE at module load to the `engineEvents` bus (which both the deck and
mixer tabs already fan their WS messages through), and seeds from
`/param-center` + `/mixer` so first paint on a cold boot is correct. The
deck and mixer tabs no longer maintain redundant per-tab state for
exports / shared params — they read the same source.

Consumers in the current codebase:

| Hook                     | Used by                              |
| ------------------------ | ------------------------------------ |
| `useEngineState()`       | Any component wanting the full snapshot. |
| `useSharedParamValues()` | `CPCControls` (sliders + colour swatches). |
| `useChannelExports()`    | `GlobalParams` (deck + mixer variants). |
| `useEngineLock()`        | `EngineLockoutOverlay` (mirrors `controlLock`). |

Adding the next live-state surface (e.g. a future "rig mode" mirror)
goes here.

## 5. Standalone Deployment (iPadOS 17+)

### 5.1 Build Pipeline

CaptainPad is deployed as a standalone `.ipa` via EAS Build (`preview` profile). No Expo Go or development server required.

```bash
eas build --platform ios --profile preview --clear-cache
```

### 5.2 iOS ATS Configuration

iPadOS 17+ no longer allows ATS connections to IP addresses by default. The app requires:

- `NSAllowsLocalNetworking: true` — enables local network IP access
- `NSAllowsArbitraryLoads: true` — backward compat for older iOS
- `NSAllowsArbitraryLoadsInWebContent: true` — WebView HTTP for Monitor tab
- `NSExceptionDomains` with universal CIDR ranges (`0.0.0.0/0`, `::/0`)
- `NSLocalNetworkUsageDescription` — user-facing permission prompt string
- `NSBonjourServices: ["_marsinengine._tcp"]` — future-proofs local network prompt

### 5.3 Local Network Permission

On first launch, iOS shows a Local Network permission dialog. If denied, all local network traffic fails silently. The Config tab includes user guidance and a deep-link to iPad Settings.

See full implementation details: `.agent/02_reports/202605/20260502_1_standalone_ipad.md`

## Scope

Implements the operator's slot 5 ask:

> with the view selection for layers, it's great, but can you also add
> locking mechanism for the layer's fader, when we lock the fader
> (separate from the layer lock), the transitions, and solo will not
> affect that layer anymore, muting will work only if enabled on that
> layer specifically!

Adds an independent `faderLocked` flag on each `PatternChannel`. When
true:

1. **Fader value frozen.** Manual writes via PATCH `/mixer/channels/:id`
   or the WS `setChannelFader` are silently no-ops (no 4xx — the next
   broadcast snaps the iPad slider back).
2. **Transitions don't touch the fader.** `triggerMixerTransition`
   skips locked overlays entirely: no force-enable, no fadeChannel
   call, no transition entry pushed. `fadeChannel()` is also short-
   circuited at the engine boundary as belt-and-suspenders. Pattern
   content swaps (playlist entry loads) still work — only the fader
   value is frozen.
3. **Solo skips locked layers** (client-side enforcement, see Design
   choice §A below). When some other channel is soloed, fader-locked
   channels stay where they are. When a fader-locked channel itself
   is the solo target, only the unlocked siblings are muted.
4. **Explicit mute still works.** `enabled=false` on a fader-locked
   channel still mutes it — fader-lock does not override an operator-
   chosen mute on this same channel. (Engine path unchanged; the
   render loop's `if (!channel.enabled) continue` gate is untouched.)

`faderLocked` is independent of `locked` (playlist/pattern lock) and
can be on/off in any combination.

## Design choices

### A. Transition semantics — skip vs. ride

The slot brief offered two interpretations: either "skip the
transition entirely for locked channels" or "let the transition's
content swap proceed but keep the fader value pinned." I chose
**skip the transition for the locked channel**. Specifically:

- `pattern_mixer.triggerMixerTransition` walks the overlay stack and
  `continue`s on `c.faderLocked` BEFORE the force-enable + fadeChannel
  step. The locked channel keeps whatever fader value the operator
  parked it at, including current `enabled` state.
- `pattern_mixer.fadeChannel` itself returns `false` immediately if
  the target channel is fader-locked, so any other code path that
  schedules fader animations (autopilot, scripted entry advances) is
  also safe.
- `loadPlaylistEntryWithTransition` is the DECK-side equivalent. It
  is unaffected because (a) the deck is its own role and (b) it
  changes pattern content via a hidden shadow channel, not by
  driving the deck channel's fader directly. A fader-locked deck
  channel's pattern content can still be swapped via the existing
  soft-swap pathway — only the deck's fader is frozen.

This matches the operator's words literally ("transitions will not
affect that layer anymore"). The alternative would have been to let
the transition proceed but freeze the fader at its current value
mid-fade, which would have left the locked layer at a brightness
that depended on the moment the lock was engaged — confusing.

### B. Solo lives client-side

Solo is not an engine concept. The CaptainPad client implements it by
mutating `enabled` and `fader` on each sibling via the existing
WS / PATCH routes, then restoring the snapshot on un-solo. The fader-
lock rule for solo is therefore enforced in `handleSoloToggle` in
`CaptainPad/app/(tabs)/mixer.tsx`: locked channels are SKIPPED from
both the save-state-and-mute branch and the restore branch. They
never appear in `preSoloStateRef`, so re-soloing or un-soloing
later cannot ever touch them. This keeps the rule symmetric with
the implementation: "solo is a client gesture; the lock-aware
client skips locked layers from that gesture."

### C. Manual fader writes — silent vs. hard reject

I chose **silent no-op + broadcast** rather than HTTP 400. Two
reasons:

- Operators bulk-PATCH multiple fields at once (name + fader + mode
  in one body). A hard 400 would block the unrelated fields from
  applying.
- The WS `setChannelFader` path is used during slider drag at
  ~100 Hz. A 400 storm would flood the client error path with no
  useful information.

The next mixer broadcast carries the unchanged fader value, so the
iPad slider snaps back within ~100 ms. WS `setChannelFader` on a
locked channel forces an immediate `broadcastMixerState()` so the
slider re-syncs without waiting for the next periodic broadcast.

### D. WRONG_ROLE preserved for /mixer route

PATCH `/mixer/channels/:id` with the deck id continues to return
HTTP 400 + `code: 'WRONG_ROLE'` (existing `rejectIfWrongRole` check
at the route entry). `faderLocked` for the deck channel is handled
via `PATCH /deck/channel`. Both routes now accept the field.

### E. State restoration plumbing fix

While adding `faderLocked` to `restoreChannel` I noticed `locked`,
`transitionMode`, and `transitionTime` were also being dropped on
engine restart (they were persisted to YAML but never plumbed back
into the `PatternChannel` constructor config). I added them to the
restore config in the same place. This is a tiny correctness win
adjacent to the slot's actual work; no behavioural change beyond
"channels now boot back into the lock state the operator left them
in" — which is exactly the same goal `faderLocked` needs.

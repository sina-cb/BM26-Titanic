# Bug Report — 2026-05-08 Session #2

## ✅ RESOLVED: sACN Universe Routing (commit `dc8d430`)

### Problem
The simulation was not receiving sACN data on Universe 2 (and beyond). The `[sACN Debug] U2 first8: null` log confirmed that Universe 2 frames were never reaching the `UniverseRouter`. The Marsin Engine was confirmed sending data for both Universe 1 and Universe 2 — the problem was input-side filtering.

### Root Cause
The sACN bridge (`simulation/server/sacn_bridge.js`) used the `sacn` npm package's `Receiver` class, which subscribes to specific multicast groups per universe at construction time. The bridge was reading `sacn_universes` from `common.yaml`, which was set to `'1'` — meaning it only subscribed to Universe 1. All Universe 2 packets were silently dropped at the UDP level.

### Fix Applied (4 files)

1. **`sacn_bridge.js`** — Replaced hardcoded universe list with `getAllPatchUniverses()` which scans ALL `scenes/*/patches.yaml` files at startup and unions every `dmxUniverse` referenced. Config override via `sacn_universes` in `common.yaml` still works (takes priority when explicitly set). Added per-universe warning for packets arriving on unsubscribed universes.

2. **`common.yaml`** — Restored `sacn_universes: "1,2,3,4,5"` under the `colorWave` section as the authoritative configuration and safety net.

3. **`patch_manager.js`** — Added `_validatePatchUniverses()` that runs on every `recompute()` call. It compares patch universe references against the `sacn_universes` config. On mismatch:
   - Logs `console.error` with 🚨 emoji
   - Shows a **fixed red banner** across the top of the screen with exact fix instructions: *"Fix: ⚡ Lighting Engine → 📡 sACN Settings → 📡 Subscribed Universes — add the missing universe(s), save, and restart the simulation."*
   - Banner is click-to-dismiss, de-duplicated (won't spam from the 10s poll)

4. **`gui_builder.js`** — Re-added the `sacn_universes` GUI control under sACN Settings so the subscribed universe list is visible and editable.

5. **`animate.js`** — Removed all temporary `[sACN Debug]` and `[sACN Out Debug]` console logging blocks that were added during troubleshooting.

### Key Pitfall Discovered
Subscribing to 256 universes crashes the bridge on Windows — the `sacn` npm Receiver joins one multicast group per universe, and Windows limits multicast group memberships to ~20 per socket. The dynamic patch-scanning approach avoids this by only subscribing to universes actually in use.

### Architecture Summary
```
Engine (sACN sender, unicast 127.0.0.1)
    → sacn_bridge.js (Receiver, subscribes to patch-derived universes)
        → WebSocket relay to browser
            → sacn_input_source.js (submits frames to UniverseRouter)
                → animate.js (demapSacnToPixels → visual rendering)
                → sACN output bridge (relays to physical controllers)
```

## 🔴 OPEN BUG: Generator-Spawned Fixtures Not Individually Selectable

### Problem
Fixtures created by the Group Generator (trace system) cannot be clicked/selected individually in the 3D viewport. When the user clicks on a fixture that was placed by a generator, the click is intercepted by the **generator trace object** (the line/path mesh), not the fixture's hitbox. The user can only select the generator itself, not the individual fixtures along it.

When generators are hidden (`generatorsVisible = false`), the user **expects** to be able to click and select the individual fixtures directly — but this does not work.

### Expected Behavior
When `generatorsVisible` is toggled OFF:
- The generator trace lines, dots, handles, and aim lines should disappear (✅ this works)
- The individual fixture hitboxes should become the primary raycast targets (❌ this is broken)
- Clicking on a fixture should select it, attach TransformControls, and open its GUI folder

### Investigation Notes

#### Selection System (`interaction.js`)
The selection system uses `raycaster.intersectObjects(interactiveObjects, false)` at line 318. The `false` parameter means it does NOT recurse into children — it only tests objects directly in the `interactiveObjects` array.

The `interactiveObjects` array contains:
- **Fixture hitboxes** — invisible `BoxGeometry` meshes with `userData.isParLight = true` (pushed by `DmxFixtureRuntime` constructor at `dmx_fixture_runtime.js:106`)
- **Generator trace objects** — line meshes, dots, start/end handles, aim handles (pushed by `gui_builder.js:1883-2001`)

#### The Issue
When the raycast fires, it tests ALL objects in `interactiveObjects`. Generator trace objects (lines, handles, dots) are registered in the same array as fixture hitboxes. Even when generators are visually hidden (`visible = false`), the trace objects may still be in the `interactiveObjects` array and blocking the raycast from reaching the fixture hitboxes behind them.

**Three.js raycast behavior**: `Raycaster.intersectObjects()` **skips objects with `visible = false`** by default. So if trace objects are properly set to `visible = false`, they should not intercept raycasts. BUT — there are several edge cases to check:

1. **Are ALL trace interactive objects being set to `visible = false`?** The `setTraceObjectsVisibility()` function (gui_builder.js) toggles `grp.visible` and `aimLine.visible`, but does it also toggle the start/end handles and dots that were pushed to `interactiveObjects`?

2. **Hitbox size**: Generator-spawned fixture hitboxes might be too small relative to the trace line meshes. The trace line mesh (`gui_builder.js:1883`) is a `TubeGeometry` with a specific radius — if it visually overlaps the fixture hitbox, it wins the raycast sort (closer intersection distance).

3. **When generators are visible**: Even when generators ARE visible, the trace line meshes intercept clicks before they reach fixture hitboxes, preventing individual fixture selection entirely.

#### Key Files to Investigate
| File | What to check |
|------|---------------|
| `simulation/src/core/interaction.js:314-365` | `onPointerDown()` — the selection handler. Check what happens when a trace object vs a fixture hitbox wins the raycast. |
| `simulation/src/gui/gui_builder.js:1718-2001` | Generator trace object construction — what gets pushed to `interactiveObjects` and how visibility is managed. |
| `simulation/src/gui/gui_builder.js:2053-2170` | `setTraceObjectsVisibility()` — verify it toggles visibility on ALL trace interactive objects (not just the visual group). |
| `simulation/src/gui/gui_builder.js:335-337` | `generatorsVisible` change handler — does it properly cascade visibility to all interactive sub-objects? |
| `simulation/src/fixtures/dmx_fixture_runtime.js:97-107` | Fixture hitbox construction — verify the hitbox is large enough to be raycastable. |

#### Suggested Fix Approach
1. When `generatorsVisible = false`, remove or disable all generator trace objects from the `interactiveObjects` array (or ensure their `.visible` is reliably set to `false` so Three.js skips them in raycasts).
2. When `generatorsVisible = true`, consider z-ordering: if the trace line mesh is closer to the camera than the fixture hitbox, the trace always wins. The fix might need to **check both intersections** and prefer fixture hitboxes over trace objects, or make trace objects non-interactive except at their control handles.
3. Consider adding a dedicated "fixture selection" pass that only raycasts against fixture hitboxes (filter `interactiveObjects` to `isParLight` entries only) when generators are hidden.

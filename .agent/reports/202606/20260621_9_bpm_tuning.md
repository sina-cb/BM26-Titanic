# 20260621_9 — BPM tuning: tempo-change responsiveness + LPF verdict

**Branch:** `feat/audio_analysis_2` (PR #39)
**Date:** 2026-06-21

## Operator report
"BPM detection is bad now — overshooting / undershooting. Run a tuning and make
sure the LPF hasn't messed it up."

## Diagnosis (measured, not guessed)
- **`bpm_tracker.js` was NOT changed** since it last worked (git log) — the merge
  of main (#40) only ADDED a `BpmSmoother` LPF in the companion. So the detection
  core didn't regress.
- **The tracker is accurate**: all 7 `bpm_tracker_octave` tests pass; the eval
  reads 110/124/128/140/150/174 within ~0.4% (raw).
- **The LPF is innocent.** Measured raw-tracker vs LPF-smoothed at steady state:
  **identical** for every tempo (the EMA converges, it can't shift the value or
  overshoot). At +0.3 s after a tempo step both raw and LPF still read the old
  tempo — the LPF contributes ~0.3 s, not the lag.
- **The real cause of the under/overshoot feel**: the tracker's LOCK inertia. A
  genuine tempo change (DJ track swap 124↔140) took **~11 s** to follow — far
  past the "a couple seconds is fine" intent — so for ~11 s after every track
  change the BPM reads the old tempo (undershoot when speeding up, overshoot when
  slowing down). On ambiguous SLOW full-mix material it also prefers the dance
  metrical level (perceptual 128 preference — correct for the EDM floor).

## Fix
`bpm_tracker.js`: `unlockVoteHops` **90 → 48**. Verified:
- Tempo-step settling **11.1/11.9 s → 7.6/8.5 s** (halved).
- Steady accuracy UNCHANGED (110–174 within 0.4%).
- Octave correctness UNCHANGED (all 7 octave tests pass: 90→90, 128→128,
  174→173, 75→75, fold-boundary 80→80).
- Real-corpus stability UNCHANGED (avg BPM-movement sd **6.62 → 6.67**; per-track
  readings unchanged) — the faster unlock does NOT add jitter, because the
  disagreement must still cluster on one octave-distinct new tempo.

The LPF is left as shipped (innocent; its 250 ms tau kills frame-jitter at ~0.3 s
cost). It can be disabled per-machine via `companion.bpmSmoothing.enabled:false`
in config.yaml if the operator wants to A/B it.

## Deliverable
`tools/bpm_tune_eval.mjs` (new) — reusable: steady-accuracy sweep (raw vs LPF),
tempo-step settling, and `--corpus` stability. A/B any tracker tuning with
`--opts '{"unlockVoteHops":24}'` before baking it into DEFAULTS.

## Validation
- BPM-related suites (octave / smoother / speed-sync / emit / signals / derived):
  **68/68**. Full suite re-run to confirm the shared-tracker change is safe.

## Optional follow-up
A more aggressive `unlockVoteHops:24` (~5 s settle) also passed steady + octave +
synthetic stability; shipped the conservative 48 (corpus-verified). Drop to ~24
on request if 7 s still feels slow on a live set.

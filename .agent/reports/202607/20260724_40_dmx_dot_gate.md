## The claim under test

> The V2 global instanced-dot flush colors every pixel — including patched DMX
> pixels — from the RAW batch entry color, NOT from the DMX-router universe
> buffer that `applyFixtureOutputOverrides` gates. So a DMX group set to OFF (or
> dimmed) may still show faint un-gated dots in the 3D render, and the 2D Pixel
> Map reads the same raw entries.

Confirmed — and **worse than filed**, for a reason the spec could not have
known: see §"The patch-state trap".

## The patch-state trap (the _27 keying lesson, one layer down)

Report _27's trap was a *group-key* mismatch. Here the trap is the *patch state*
of the show scene:

```
$ grep -c "dmxUniverse: [1-9]" simulation/scenes/titanic/patches.yaml
0
```

**The titanic show scene has ZERO patched DMX fixtures** (`_patchesActive ===
false`, the "⚠ UNPATCHED — SIM-ONLY MODE" badge is up in every render). In that
state `applyFixtureOutputOverrides` **does nothing at all** — it `continue`s past
every fixture whose universe is `< 1` — and `applyDmxFrame` never runs either. So
the premise "the bulbs are already gated by the buffer, only the dots leak" holds
for a patched rig but **not for the scene the operator actually runs**. There,
`entryPaintsDirect()` is true for every DMX entry and the fixture bulbs are
direct-painted straight from the same un-gated entry color as the dots.

Net: in the show scene the DMX group master had **no effect on any rendered
pixel whatsoever** — dots, 2D map *and* bulbs. Only the light pool honoured it
(`light_pool.js` skips a fixture whose `outputGain() <= 0`), which is why turning
a group off did visibly change the ground pools while the fixtures themselves
stayed lit — a very confusing half-effect.

Both regimes are therefore verified below, not just the one in the spec.

**Why those two are already safe:** `applyFixtureOutputOverrides` runs as the

`outputGain() <= 0`, so an off group frees its SpotLights.

## The fix — one authority, applied after every color source

**`dmxOutputScale(config, groupOverrides) → 0..1`** (new, pure, in
`src/dmx/dmx_output_overrides.js`) is now THE one authority for how much of a DMX
fixture's light reaches anything: the group ▸ fixture combined override
(`resolveCombinedOverride`, unchanged) collapsed to a scalar. Off ⇒ 0; else the
effective brightness fraction (1 at ≥ 100 %, so a full-on fixture is a byte-exact
no-op).

- **`applyDmxEntryOutputGate(entry, groupOverrides)`** (new, same pure module)
  scales one batch entry's `r/g/b/w/a/u` **in place**. Pure — no THREE, no DOM —
  so the render loop's gate is unit-testable.
- **`_applyDmxOutputGate(list, headless)`** (new, `animate.js`) walks the list for
  `entry.type === 'dmx'`. **One call site**, deliberately placed *outside* the
  `if (window.dmxRouter)` block, **after** `applyFixtureOutputOverrides` +
  `applyDmx()` and **before** the V2 dot flush and `_dispatchPixelFrame()`:
  - after the buffer gate, so a dimmed group is scaled **exactly once** on the
    wire — putting it before `mapPixelsToSacn` (where the LED gate sits) would
    have dimmed the sACN output twice;
  - outside the router block, because the unpatched regime — where the buffer
    gate does nothing — is precisely the case that needs it.
  Entries are rewritten from scratch by every color source each frame (gradient,
  pattern engine, `demapSacnToPixels`, the lighting-disabled clear), so the
  in-place scaling cannot compound.
- **Direct-paint repaint.** When the gate actually bites (`scale < 1`) and the
  entry direct-paints (`entryPaintsDirect(entry, window._patchesActive)` — true
  for DMX only while nothing is patched), it re-calls `entry.apply()` with the
  gated blend so the bulb/halo/cone match the dots. Patched entries never take
  this branch: `applyDmxFrame` owns their visual, from the already-gated buffer.
  Skipped in headless.
- **`entry.fixtureConfig`** (new, `pixelblaze_model_exporter.js`, both DMX pixel
  shapes) is the join. It is the **same live config object** that
  `applyFixtureOutputOverrides` reads as `fixture.config` — not a group-name
  string — so the two gates *cannot* key differently, and the per-fixture
  On/Off + Brightness comes along for free. Runtime-only: it is not in the
  `saveModelJS` field list, so the engine model is byte-identical (there is a
  test that asserts the string `fixtureConfig` never appears in the generated
  model). LED pixels deliberately do **not** carry it — they stay on
  `ledOutputScale` / `entry.displayGroup`, untouched.
- **`DmxFixtureRuntime.outputGain()`** now delegates to `dmxOutputScale` (its
  duplicated `enabled/brightness → gain` math is gone), so the static preview and
  the light pool derive from the same single function. No behavior change — a
  unit test pins entry-gate ↔ buffer-gate parity across the override matrix.

Scope held: no LED-gate edits, no `gui_builder.js` edits (concurrent-agent
territory), and the tree's uncommitted `color_transition` gradient-LUT work in
`animate.js` was left exactly as found.

Cost: measured at **0.013 ms/frame** for 990 entries (≈0.05 % of a 25 ms frame) —
no memoisation needed.

## Tests

`cd simulation && npm test` → **542 pass / 0 fail** (baseline 526; +16 from the
new `tests/dmx_output_gate.test.js`). `node --check` clean on every edited file.

New cases cover: the scale math and clamping; group-vs-fixture priority; the
**keying trap** (an ungrouped `config.group` must ignore a `Default`/`Ungrouped`
bucket exactly like the buffer gate does — a gate that "helpfully" bucketed it
would black out fixtures the wire keeps lit); a **parity matrix** asserting the
entry gate and `applyFixtureOutputOverrides` can never disagree; in-place RGBWAU
semantics incl. byte-exact no-op at full-on and idempotence; the exporter
attaching the *same object identity* on both DMX pixel shapes and **not** on LED
pixels; and that `fixtureConfig` never reaches the generated engine model.

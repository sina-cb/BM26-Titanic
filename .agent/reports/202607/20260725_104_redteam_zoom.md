## 0. Headline

The **engine's "never stuck" invariant holds** — I could not construct a zoom
the rig cannot leave. Every exit funnels through `resume()`/`_catchUp`, and I
verified each guard independently (§3). **The break is on the PAD**: a
module-level exit-claim latch (`_zoomExitRequested`) **leaks** through the plain
(non-zoom) takeover-resume path and then **silently swallows the "zoom ended"
safety notice** on the next engine-imposed zoom exit — the operator is dropped
onto a deck they no longer own with no explanation. That is the exact
protection `_97` §3.4 added, inverted.

| # | Severity | Category | One-liner |
|---|---|---|---|
| **A1** | **HIGH** | silent-fallback / pad-lying | `_zoomExitRequested` leaks via the plain-takeover RESUME NOW → the "Zoom ended — the plan resumed" toast + auto-nav is suppressed on the next engine-imposed zoom exit |
| **A2** | **MED** | quirk / latent stuck-state | The scoped zoom lease IS written to `timeline_state.yaml` (scope/cueId/label/target); only the one-line boot `_catchUp` scrub prevents a rebooted ship waking with a ghost PERFORM banner (confirms `_100` F1, ordering independently verified) |
| **A3** | **MED** | silent-fallback / pad-lying | The D3 "Show due: X — starts when you exit" banner keeps promising a show that `_catchUp` will silently SKIP if you linger in the zoom past the cue's hold window; EXIT and ENABLE then diverge |
| **A4** | **LOW** | quirk (spoofable label) | The engine does not check a PERFORM `cueId` is the live/active cue — only that it exists — so a client that bypasses the pad guards can arm "PERFORMING <any cue>" |
| **A5** | **LOW** | quirk | Travel steppers use strict `>`/`<` on fire instants, so two co-timed cues can never both be reached by prev/next |

**Top 3: A1 (HIGH), A2 (MED), A3 (MED).** `config.yaml` clean: **YES.**

## 1. What I could NOT break (the invariant held — recorded so the next
red-teamer doesn't re-plough it)

All verified by reading the landed code paths, not by belief:

- **`resume()` can't leave a stuck zoom even if catchUp throws.**
  `timeline_service.js:2974-2976` sets `mode='armed'` and `operatorLease=null`
  **before** `await this._catchUp()`, and the catchUp call is wrapped in
  try/catch (`:2977-2982`). So `_zoomLease()` (which requires
  `mode==='overridden'`, `:2620`) returns null the instant resume runs,
  regardless of any downstream failure. The REST route's own `.catch(500)` is
  moot — the lease is already gone synchronously.
- **The tick always releases an expired lease before it does anything else
  with it.** Dormancy gate first (`:2117`), then lease-release
  (`:2146-2156`: `mode==='overridden' && (no lease || now>=expiry)` →
  `_releaseOperatorLease` → catchUp), then the orphan self-heal
  (`:2163-2166`, drops a lease on a non-overridden mode). A stranded
  `overridden`-without-lease and a lease-without-`overridden` are BOTH
  self-healed.
- **Boot scrub ordering is safe.** `start()` (`:355`) runs `_loadSceneFiles()`
  (loads the persisted, possibly-stale lease) then `await _catchUp()`, whose
  lease-null + `mode='armed'` scrub (`:1893-1908`) is **all synchronous, before
  any `await` inside catchUp and before the first `_broadcastState()`
  (`:387`)** — no event-loop yield, so nothing can observe the stale lease
  (WS connect replay, `/timeline/state`) between load and scrub. (This is what
  makes A2 latent, not live.)
- **`_goDormant` cannot strand a travel zoom.** `:1666-1675` keeps only an
  **unexpired** `scope:'travel'` lease; an expired one is nulled and `mode`
  reset right there, and the out-of-window tick returns before the normal
  lease-release path (`:2117-2128`). Presence pings (`activity()`, `:3082`)
  still refresh it while dormant because it keeps `mode==='overridden'`.
- **Malformed `POST /timeline/travel` all 400 with no state mutation.**
  `_resolveTarget` (`:2688`) throws for `{date}` without `{time}`
  (`:2732`), a non-YYYY-MM-DD date (`:2713`), a bad HH:MM (`:2735`), an
  unknown/undated/non-clock-sun `cueId` (`:2724`), and `step` with no active
  travel (`:2699`) — and `travel()` calls `_resolveTarget` **before** touching
  the lease (`:2825`), so a bad body leaves any existing zoom intact.
- **Step-past-the-end 400s cleanly.** `no next/prev event on <date>`
  (`:2707`) throws pre-mutation; the banner prints it verbatim; the lease is
  untouched.
- **Two-client one-writer is last-write-wins by design (D6)** — B's
  travel/perform overwrites the single `operatorLease`; both pads render the
  same broadcast; no second lease object exists to orphan. A's `resume()`
  ends it for both; that is the intended "one crew, one rig."
- **Plan save / activate / autopilot-off / program-enable** each null the
  lease (`:2952`, `:2978`, `:3140`, `:3207`) → `_zoomWire()` returns null → the
  zoom is structurally gone.

## 2. Findings

### A1 — HIGH — the exit-claim latch leaks and then eats the "zoom ended" alarm

**Category:** silent-fallback / pad-lying (the "nobody can walk up to a pad and
not know" and "learn WHY the deck changed under them" intent, defeated).

**Where.** `CaptainPad/hooks/useTimeline.ts` + `components/timeline/ZoomBanner.tsx`.

**Mechanism.**
1. `_resume()` stakes the exit claim **unconditionally** on every call:
   `_zoomExitRequested = true;` (`useTimeline.ts:171`), before the request goes
   out. On success it also clears `_zoomEnteredHere` (`:184`) but **leaves
   `_zoomExitRequested` set** — that flag is only ever cleared by
   `clearZoomClaims()`.
2. `clearZoomClaims()` is called from **exactly one place**:
   `ZoomBanner.tsx:88`, inside `if (hadZoomRef.current && !has)` — i.e. only
   when the banner observes a real **zoom → null** transition (`:79-97`).
3. `_resume` is **also the plain-takeover hand-back.** `useOperatorTakeover`
   returns `resumeNow: resume` (`useTimeline.ts:453`), wired to the deck's
   RESUME NOW (`app/(tabs)/index.tsx:955`) and the `PlanLockBanner`'s RESUME
   NOW (`PlanLockBanner.tsx:208`). A plain takeover has **no zoom**, so pressing
   RESUME NOW sets `_zoomExitRequested=true` and there is **no zoom→null
   transition** to trigger `clearZoomClaims()`. The flag is now **stuck true**.

**The break.** Later the operator enters a real PERFORM/TRAVEL zoom
(`_zoomEnteredHere=true`, `:284`/`:298`). The engine then imposes an exit the
operator did NOT ask for — lease expiry (walked away), engine restart, autopilot
OFF from another pad, or the maker's auto-save. The banner's effect fires with:

```
ours    = zoomExitRequested()  // TRUE (stale leak)
entered = zoomEnteredHere()    // true
shouldAnnounceZoomEnd({ours:true, entered:true}) === false   // zoom_logic.ts:231
```

→ **no "Zoom ended — the plan resumed at now." toast, no `router.push('/timeline')`**
(`ZoomBanner.tsx:89-94`). The operator is left on the deck tab, the banner
silently gone, with no idea the rig was handed back to the plan. This is the
precise failure `_97` §3.4 built the claim to prevent — over-corrected into
suppression.

**Why the tests miss it.** `zoom_logic.test.ts:227-247` only exercises the PURE
`shouldAnnounceZoomEnd`, which is correct. The defect is in the **stateful
`ours` input** — the leaky module-level latch — which nothing tests.

**Repro (logic-level; deterministic, no engine needed to see the leak):**
1. Do any plain takeover (grab a deck fader), then tap RESUME NOW. →
   `_zoomExitRequested` is now `true` and stays true.
2. Open an event and tap PERFORM (or TIME TRAVEL). → `_zoomEnteredHere=true`.
3. Cause an engine-side exit: let the presence lease expire (background the
   app ~2 min), or restart the engine, or toggle the plan's autopilot OFF from
   a second pad.
- **Expected:** "Zoom ended — the plan resumed at now." toast + snap back to
  the TIMELINE tab (this is what happens if step 1 is skipped).
- **Observed:** banner vanishes, no toast, no navigation — the operator is
  silently stranded on a deck the plan has reclaimed.

**Fix options (pick one):** (a) in `_resume`, only stake the claim when a zoom
is actually held (`if (_cached?.zoom) _zoomExitRequested = true;`); (b) always
clear `_zoomExitRequested` once resume resolves (success OR the zoom is already
null); (c) reset both claims on WS reconnect / in `_reseedAfterAction`. (a)+(b)
together are the tightest.

### A2 — MED — the "runtime-only" scoped lease is persisted; only one line saves the reboot

**Category:** quirk / latent stuck-state. Confirms `_100` F1; I independently
verified the write path AND the scrub ordering.

`saveTimelineState` (`timeline_state.js:238-244`) `yaml.dump`s the **entire**
`state`, and the scoped lease lives on `state.operatorLease` with
`scope`/`cueId`/`label`/`targetMs`/`targetDate` (`timeline_service.js:3044-3055`,
`:2836-2843`). Every changed tick therefore writes the whole zoom to
`marsin_engine/states/<scene>/timeline_state.yaml`. The design language in both
`_94` §4.3 and `_95` §3.5 ("runtime-only", "structurally un-strandable")
describes the SEMANTICS, not the bytes.

The **only** thing between a persisted `scope:'perform'` lease and a rebooted
ship that wakes believing a human owns the deck — a stuck PERFORM banner, i.e.
the "never stuck" invariant broken — is the single boot scrub
`this.state.operatorLease = null` (`:1901`) + `mode='armed'` (`:1908`). I
confirmed it runs synchronously before the first broadcast (§1), so this is
**latent, not live**: `_100` X6 proves the scrub end-to-end for both scopes.

Reported because the guarantee is one deleted-line-away from structural and one
regression-away from a stuck banner on a rebooted ship. **Fix:** omit
`operatorLease` (and `pendingProgram`) from the serialized shape in
`timeline_state.js`, or persist them always-null. Outside this thread's
report-only scope; flagged for a `timeline_state.js` follow-up.

### A3 — MED — the deferred-show banner promises a show that a lingered exit silently skips

**Category:** silent-fallback / pad-lying.

D3 defers a due program by pushing its `pendingProgram.expiresAtMs` out to the
zoom lease's expiry every tick (`timeline_service.js:2199-2204`), and
`_zoomWire().pendingDeferred` keeps surfacing it from `state.pendingProgram`
(`:2644-2652`) for as long as the zoom is held. The banner renders **"⚠ Show
due: X — starts when you exit"** (`ZoomBanner.tsx:179-193`,
`zoom_logic.ts:181-185`).

But the exit fires the show **only if its hold is still live at exit time.**
`resume()` → `_catchUp` → `resolveDeckStateAt`: `programLive = holdUntilMs > atMs`
(`resolve_deck_state.js:166`); if the operator lingers past `fireMs + hold`,
`programLive` is false, catchUp re-applies the LOOK but does not seize control
(`timeline_service.js:1939-1945`, `:1973-1983`), and `_reconcileDefaultCue`
reclaims the deck. The show is **silently skipped** — the design's "honestly
skipped" (`_94` §3.2) — **while the banner still promised it would start on
exit.** The pad copy lies for that whole window.

Worse, the two controls **diverge**: EXIT honors the original (elapsed) hold and
skips; **ENABLE** (`enableProgram`, `:3208-3212`) starts it with a **fresh** hold
`resolveHold(hold, now, …)` from now, so it plays. Same banner, two outcomes, no
hint which.

**Repro:** PERFORM a live event; while zoomed, let a short-hold program cue come
due (banner shows the deferred line); wait past that cue's hold window; tap EXIT.
- **Expected (per banner):** the show starts.
- **Observed:** its look flashes, the default cue reclaims — it never runs as a
  program. (ENABLE at the same moment WOULD run it, fresh.)

**Fix:** when the deferred cue's hold has elapsed, drop `pendingDeferred` from
the wire (banner stops promising) or change the copy to "can be started with
ENABLE" — never keep saying "starts when you exit" once exit won't start it.

### A4 — LOW — engine trusts the client's PERFORM `cueId` (no live-cue check)

`takeover({scope:'perform', cueId})` validates only that the cue **exists** in
the active plan (`timeline_service.js:3013-3020`) — not that it is `activeCue`,
applicable today, or even a deck cue. A client that bypasses the pad's guards
(`eventZoomMode`/today-scoping, the very thing `_97` §4.3 had to add live) can
arm a lease whose banner reads "PERFORMING <arbitrary cue>" while a different
cue, or none, is actually live. The takeover itself is harmless (it just freezes
the deck manually), but the label lies and the engine is the wrong place to be
defenceless about it. **Defense-in-depth:** reject a `perform` `cueId` that is
not the current `activeCue`.

### A5 — LOW — co-timed events are unreachable by the travel steppers

`_resolveTarget` step uses strict `atMs > from` / `atMs < from`
(`timeline_service.js:2704-2706`). Two cues resolving to the **same instant**
(e.g. two `sun`-anchored cues at the same computed minute) can never both be
stepped to — prev/next skips the co-timed sibling and jumps to the next distinct
time. Minor navigation gap; a `cueId` target still reaches either directly.

## 3. Cross-check against the exit table (`_94` §5) and the attack list

Every row I could reach, and the combinations `_100` could not test:

| Attack | Verdict |
|---|---|
| Two/three clients same/different events | one-writer last-wins (§1); no orphan; B renders A's zoom; either EXIT ends both — **by design (D6)** |
| A performs, B force-takes (travel), A's EXIT | lease is B's (overwritten); A's resume clears the single lease → both exit. No leak |
| Engine restart at the tick a lease is granted | grant is sync + atomic write; boot scrub nulls it either way — **safe** (see A2 for the latent-persistence caveat) |
| Plan save while traveling to a cue the save deletes | savePlan → catchUp drops the lease & re-derives from NOW; stale `cueId`/`targetDate` discarded — safe |
| Travel, step past both ends repeatedly | 400s pre-mutation, lease intact — safe (A5 is the only quirk) |
| Travel while dormant, then the window opens under you | `_goDormant` keeps the unexpired travel lease; in-window tick resumes normal eval; exit → catchUp — safe |
| D3 deferred cue whose hold passed by exit | **does NOT fire stale** engine-side (correct) — but the BANNER lies about it → **A3** |
| Lease expiry mid-perform vs a program due same tick | tick order = release-lease → catchUp (fires it if hold live) BEFORE arbitrate; deferral only runs while the lease is alive; no double-fire — safe |
| The `_97` cleared-zoom-beats-resume race under load | pre-staked claim handles it — but the claim's latch **leaks** → **A1** |
| Zoom persisted to `timeline_state.yaml` surviving a stale restore | **A2** |
| Malformed `POST /timeline/travel` bodies | all 400 pre-mutation (§1) — safe |

## 4. Hardening recommendations (priority order)

1. **A1 (do first):** stop `_zoomExitRequested` leaking — stake it only when a
   zoom is held, and clear it whenever a resume resolves. Add a stateful test
   that drives `_resume` (plain) → perform → engine-imposed null and asserts the
   toast fires. This is the one that will actually mislead the operator on a
   show night.
2. **A2:** make "runtime-only" structural — omit `operatorLease` /
   `pendingProgram` from the serialized state so a reboot can never carry a
   ghost lease even if the scrub regresses.
3. **A3:** make the deferred banner honest once the hold elapses (drop the line
   or re-word it to ENABLE-only), so EXIT and the banner agree.
4. **A4:** validate a PERFORM `cueId` against `activeCue` engine-side.
5. **A5:** use `>=`/`<=` with a `!== current cueId` guard in the stepper so
   co-timed events are reachable.

Also worth an operator ruling (already flagged by `_100` F2, not re-litigated
here): entering ANY takeover stands the deck's pattern autopilot down, so a
PERFORM freezes the look's cycling under the performer.

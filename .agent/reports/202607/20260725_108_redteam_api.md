# `_108` — RED-TEAM: engine HTTP/WS API contract + CaptainPad client

**Adversarial thread.** Mission: break the engine's HTTP/WS API and the
CaptainPad client that consumes it — malformed requests, protocol races, enum
drift, concurrent writers, reconnection storms. Report-only: **no source edits,
no tracked-suite edits**. All repros in `~/tmp/redteam_api/` (gitignored).

Attack surface owned: `marsin_engine/lib/api_server.js` (all REST + `/ws/*`),
the CaptainPad TS API/WS layer (`utils/party_api.ts`, `utils/timelineApi.ts`,
`hooks/useTimeline.ts`, the timeline tab consumers). Context weaponised: `_87`,
`_95`/`_97` (zoom API + the `effectiveState` enum coupling), `_96`, `_98`
(triggerArmed-not-a-7th-enum), `_99` (the unhandled EventEmitter `'error'`
lesson), `_100` (the subprocess-engine e2e harness — reused directly).

Every engine here was a **black-holed throwaway** spawned via
`tests/e2e/timeline_e2e_harness.mjs` (`controllers: []`,
`sacn.destinations: [127.0.0.9]`, `MARSIN_CONFIG_FILE`/`STATE`/`PLAYLISTS`/
`TIMELINE` redirected, random port 7700-7899). Zero device HTTP, zero sACN to
hardware. The operator's stack (:6969-:6972) was never touched.
`marsin_engine/config.yaml` is **CLEAN vs HEAD** at hand-off.

**The HTTP surface is genuinely hard.** Hundreds of malformed / missing / extra

## 1. CRITICAL — a single malformed WebSocket frame crashes the engine

**Category: engine-crash (the `_99` sibling the brief asked to hunt).**

### Repro
`~/tmp/redteam_api/ws_crash.mjs`. Spawn a black-holed engine, complete a normal
WS handshake to `/ws/control`, then send ONE client-masked **text frame whose
payload is invalid UTF-8** (`0xFF 0xFE 0xFD`). Observed:

```
⏱ Timeline service started (scene "test_bench", plan "zoom_e2e")
node:events:487
      throw er; // Unhandled 'error' event
      ^
Error: Invalid WebSocket frame: invalid UTF-8 sequence
    at Receiver.dataMessage (…/node_modules/ws/lib/receiver.js:583:28)
    …
Emitted 'error' event on WebSocket instance at:
    at Receiver.receiverOnError (…/node_modules/ws/lib/websocket.js:1204:15)
  code: 'WS_ERR_INVALID_UTF8', Symbol(status-code): 1007
Node.js v24.18.0
```

The process **exits**. `GET /status` fails immediately after
(`engine alive: false`). Confirmed **independently on `/ws/params`** as well —
each of the four topic servers is its own `WebSocketServer`, and none attaches a
per-client error listener, so all four (plus the transitional `/` alias) are
vulnerable.

### Root cause
`api_server.js` builds four servers (`api_server.js:9782-9785`) and, per server,
attaches only `wssInst.on('error', …)` (`:9807`) and a process-level
`server.on('error', …)` (`:9852`). The **per-connection** handlers registered in
each `wssX.on('connection', ws => …)` block are `ws.on('message', …)` (wrapped
in try/catch, so bad JSON is safe) and `ws.on('close', …)` — **but no
`ws.on('error', …)`**. When the `ws` receiver hits a frame/UTF-8/close-code/
opcode/RSV violation it emits `'error'` on the *WebSocket instance*; an
EventEmitter `'error'` with no listener throws, and with no
`process.on('uncaughtException')` anywhere in `engine.js`/`api_server.js` the
process dies. This is exactly `_99` §2.3 — a `packet`/`message` listener present,
the `error` twin missing — relocated from the sACN receiver to the control bus.

### Why this is the worst finding on the surface
- **No malice required.** Invalid UTF-8, a reserved opcode, an oversize control
  frame, a bad close code, or a frame corrupted by a flaky playa WiFi link all
  land here. Any non-`ws` client (a hand-rolled reconnect, a proxy, a fuzzer,
  someone's laptop on the LAN) can do it by accident.
- **The blast radius is the whole ship, with no self-heal.** `launcher.js:623`'s
  child-exit handler does **not** restart a crashed engine — after
  `CRASH_VERDICT_DELAY_MS` it logs *"exited unexpectedly … Tearing down"* and
  calls `teardown(1)`, killing the entire stack. There is no supervisor
  respawn. One bad frame = lights out until a human runs `launcher.js prod`
  again. Repeating the frame re-kills it. This is the mission-critical
  "dark ship" failure.

### Fix (recommended)
Attach a classified, **non-fatal** per-connection error handler in every
`wssX.on('connection', ws => …)` block — the same shape `_99` gave the sACN
receiver:

```js
ws.on('error', (err) => {
  console.warn(`[ws/${topic}] client socket error (${err.code || err.name}): ${err.message}`);
  try { ws.close(1002); } catch {}   // protocol error; drop THIS client, keep the engine
});
```

A frame error is a *per-client* fault and must cost only that client, never the
render loop. Belt-and-braces: add a loud `process.on('uncaughtException')` /
`process.on('unhandledRejection')` in `engine.js` that logs and (for the show
profile) is the last line of defence — but the real fix is the per-socket
listener; a bare process handler would mask the class of bug rather than isolate
it. Pin it with a test that drives a real `Receiver`-violating frame at each
topic and asserts the process stays up (mirrors `_99`'s live regression pins).

## 2. MED — the `effectiveState` enum is a hard engine↔pad coupling

**Category: enum-drift.**

`CaptainPad/utils/party_api.ts:173` — `parsePartyConfig` **throws** on any
`effectiveState` outside the six-value set `['armed','disabled','no_plan',
'manual','in_session','cooldown']`. The engine producer
(`timeline_service.js:1414-1420`) is currently closed to exactly those six, so
there is **no live drift today** — and `_98` deliberately added the additive
`triggerArmed` boolean rather than a 7th enum for precisely this reason.

**Good news the brief did not assume:** a drifted value would **not crash the
pad**. All three consumers wrap the throw —
- `fetchPartyConfig` (`:237`) → `{ ok:false, error }`,
- `setPartyConfig` (`:255`) → `{ ok:false, error }`,
- the WS `partyConfig` broadcast handler (`timeline.tsx:1509`) → `setLoadError`.

**The residual risk (why it is still MED, not closed):** the coupling is
brittle in the *forward* direction. The day anyone adds a legitimate seventh
engine state (a plausible future — e.g. a distinct "blocked by program" state,
which `_98` §8.3 already wanted), **every deployed pad that predates the change
puts its entire PARTY card into a permanent error banner** on an otherwise
healthy engine — a contract-lie by omission (the card can't render a state the
engine validly holds). An additive contract should degrade, not hard-fail:
`parsePartyConfig` should accept an unknown `effectiveState` as a pass-through
string and let `describePartyStatus` fall to its existing `default: break`
derivation (`:451`), which already handles "no known state" gracefully. Reserve
the loud throw for *type* violations (non-string), not *value* drift.

## 3. LOW findings

### 3a. `POST /timeline/takeover` coerces a garbage body into a plain takeover
**Category: silent-clamp / fallback (codex P0-adjacent).** Bodies `null`, `123`,
`"hi"`, `[]`, `true`, `1e999` all return `200 {ok:true, operatorLease:{…},
zoom:null}` — a real armed lease. The contract (`_95` §3.3) is "bodyless =
plain takeover", and these non-object JSON values silently *become* bodyless.
A CaptainPad bug that PUTs a malformed takeover body would silently grab the
deck instead of surfacing a `400`. Recommend: reject a present-but-non-object
body with `400` (an absent body stays the plain-takeover path). Repro:
`~/tmp/redteam_api/probe.mjs` §1-2.

### 3b. Concurrent `takeover(perform)` + `travel` — the winning response lies
**Category: write-race.** Firing `POST /timeline/takeover {scope:perform,
cueId:c_live}` and `POST /timeline/travel {cueId:c_morning}` in the same tick:
**both return `200`**, but the final `GET /timeline/state.zoom` is the travel
one (last-writer). The takeover's own `200` body reported its `zoom` as the
resulting state — a momentary lie for the client that lost the race. Self-heals:
the next `timelineState` broadcast (≤1 s) reconciles both pads to the real
single-session zoom, and `_97`'s pre-staked exit claim already anticipates the
broadcast-beats-response ordering. Reported for completeness — the response
should arguably reflect post-reconcile state, or the loser should get a `409`.
Repro: `probe.mjs` §9.

### 3c. `/timeline/resolve` with a very long query → `431`, empty body
**Category: quirk.** `GET /timeline/resolve?date=<20 000 chars>` returns Node's
built-in `431` with an **empty (non-JSON) body**. The EventSheet resolver
consumer (`_97` §3.1) surfaces engine 400s verbatim but here would show
`HTTP 431` with no `{error}`. Harmless (no crash), but the one resolve response
on the surface that isn't a JSON `{error}`. Repro: `probe.mjs` §4.

### 3d. `/timeline/resolve` matches by `startsWith`
**Category: quirk.** `api_server.js:6092` routes `req.url.startsWith('/timeline/
resolve')`, so `/timeline/resolvexyz` matches the resolver (→ `400`) instead of
`404`. Cosmetic; no security or crash impact (the query parser ignores the
suffix). Every *other* timeline route uses exact `===` match. Repro:
`probe.mjs` §4.

## 4. What was tried and held (the hardening that works)

- **REST fuzz, zero crashes.** takeover / travel / resolve / party-config /
  plan-activate / plan-save / wrong-method / unknown-route, each with malformed
  JSON, non-object bodies, wrong types, out-of-range numbers, `1e999`,
  `MAX_SAFE_INTEGER`, `../../` traversal, NUL, emoji, 10 KB+ strings, SQL-ish
  strings, `__proto__` in the body — all clean `400`/`404`/`405` with a verbatim
  `{error}`. No `500` on user input, no unhandled rejection. (`probe.mjs`,
  `deaths: 0`.)
- **No silent clamp on party-config.** Every out-of-range value is *rejected*
  loudly (`must be 0..3600`, `must be 1..120`, `unknown playlist …`,
  `unknown field …`), not clamped. (One tiny quirk: `minDwellSec:15.5` is
  accepted verbatim — non-integer dwell; harmless, worth an `assertInteger` if
  the operator cares.)
- **WS reconnection storm** (60 rapid connect/close) and **garbage/oversize
  text frames** (valid-UTF-8 non-JSON, `[]`, `null`, 200 KB string) — engine
  stayed up (the `message` handler's try/catch holds; the crash in §1 is the
  *frame* layer, below `message`).
- **Enum producer** closed to six values; `_isTimelineState` guard is lax
  (only checks `mode` is a string) so no risk of silently dropping drifted
  `timelineState` frames.
- **festival.days bounded [1,31]** (`show_plan.js:561`) → `buildOverview`'s
  per-day loop cannot be driven into an event-loop wedge.

## 6. Recommendations (ranked)

1. **[CRITICAL] Add per-connection `ws.on('error')` to all four `/ws/*`
   servers** (§1) + a test driving a frame violation per topic. This is the one
   that keeps the ship lit.
2. **[MED] Make `parsePartyConfig` degrade on unknown `effectiveState`**
   instead of throwing on value (§2) — pass the string through, let
   `describePartyStatus` derive; keep the throw for type violations only.
3. **[LOW] `POST /timeline/takeover`: reject a present non-object body with
   `400`** (§3a) — close the silent plain-takeover fallback.
4. **[LOW] Consider `409`/post-reconcile response for conflicting zoom writers**
   (§3b) and a JSON error body / exact-match route for `/timeline/resolve`
   (§3c/§3d).

# 368 — S5: the HIL tooling (`hil_push_check.cjs`, `hil_serial_tail.py`, mock suite)

Implements slice **S5** of `_363` (§6 in full) plus its `tests/hil_push_check.test.js`
block from §5. **TOOLING ONLY — nothing was run against any hardware.** No HTTP
request left this machine, no serial port was opened, no device was contacted, the
runner's run body was never executed against a target, and the mock suite neither
spawns the runner nor the capture helper. No git operation.

Controllers are named by `controllerId`; IPs appear as last octet only, and every
test fixture uses the documentation range.

---

## 1. Objective

Build the hardware-in-the-loop harness `_363` §6 specifies — a Node driver that
drives the REAL narrowed push + DMX toggle through the same client functions the
Controllers panel calls, a pyserial capture helper for the independent serial
evidence channel, and a mock-only suite that gates every pure helper offline —
so the operator-announced S6 run has something safe to run. Gamma is out of the
runner entirely (`_364` ruling; `_363` §11's `--gamma` leg is FUTURE and was not
built).

## 2. What shipped

| `buildRestoreBody(snapshot)` | PURE | `{strands, dmx}`, deep-copied |

| `renderTable(report)` | PURE | the §6.5 block + verdict |
| `mainWasInvoked()` / `main(argv)` | hook / run body | inertness proof + the run |

Run order per target, sequential (§6.4): PREFLIGHT (allowlist → identity →
capability → serial attach) → SNAPSHOT (written and its path printed FIRST) →
CONFIG leg → TOGGLE off leg → TOGGLE on leg → RESTORE with deep-equal verify.
`--skip-config` / `--skip-toggle` / `--no-serial` / `--expect-universes` per
§6.1; no flag widens targeting, and `--no-serial` caps the verdict at
`PASS (HTTP-only — not gate evidence)`.

### `simulation/tools/hil_serial_tail.py` (new)

pyserial capture helper. `import serial` / `import serial.tools.list_ports` at the
top — a missing dependency crashes at start (P0). Two modes: `--list` enumerates
the ports with description, `VID:PID` and serial number so the operator can map a
board to a COM port; `--port COM7 --out <log>` appends `<ISO-timestamp> <line>`
for the whole run and prints `HIL_SERIAL_READY <port>` once attached. `open_quiet`
builds an unopened `serial.Serial()`, sets `dtr = False` and `rts = False`, and
only THEN opens — the default open asserts both lines and resets the chip, which
would both fake a boot in the evidence and reboot a live show board.

### `simulation/tests/hil_push_check.test.js` (new, 40 tests)

Mock-only, offline, no spawn: allowlist refusals, the flag gate, the
snapshot-derived plan, the restore body, the serial classifier, table rendering,
and the inertness assert.

## 3. Design notes

**`require(esm)` for the real client.** The runner reuses the REAL functions —
`buildForcedConfigBody`, `pushForcedConfig`, `diffForcedConfig`,
`swarmEnabledNote`, `buildDmxToggleBody`, `diffDmxToggle`, `pushDmxToggle`,
`awaitReboot`, `deviceSupportsPerOutput`, `getStatus`, `getConfig` — via a plain
top-level `require('../src/dmx/led/marsinled_client.js')`. `marsinled_client.js`
is a browser ES module inside a CommonJS package; Node's native `require(esm)`
(>= 22.12, this project runs 24.x) bridges it synchronously, exactly the
precedent `server/led_gamma_service.cjs` already set. Verified in-process: the
require returns 29 named exports. There is no second implementation of the
contract anywhere in the runner, and no dynamic `import()` — an older Node
crashes at the require, which is the correct loud failure.

**The plan is derived from the board, not from the sim.** The runner never reads
a scene. `buildPlanFromSnapshot` re-asserts the board's CURRENT mapping (each
enabled strand with an integer `dmxUniverse` → `{outputIndex, universe,
pixelCount}`), so the config leg proves transport, reboot, verify and serial
health without changing what the board drives; the real state-change proof is the
toggle leg. Two refusals guard it: no enabled per-output strand ("push it from
the sim once first"), and an enabled strand missing a universe or a sane count —
planning around that one would DARKEN a live output, so it is a hard refusal
rather than a silent disable.

**Serial classifier heuristics** (all `classifySerialWindow`, all mock-tested):

- *Boots* — the public ESP32 boot-ROM banners (`ESP-ROM:`, `rst:0x…`, the `ets`
  banner). Three banner lines of ONE boot arrive milliseconds apart, so markers
  within `BOOT_COALESCE_MS` (2000 ms) count once. Two boots in one leg window is
  the crash-loop shape and fails the leg; a boot in the OTHER target's window
  fails the run naming the suspected `--serial` swap.
- *Crashes* — ESP-IDF-generic fatals only: Guru Meditation, `panic'ed`,
  `abort() was called`, assert-failed, task/interrupt watchdog, brownout, corrupt
  heap, `Backtrace:0x…`, plus a reset-reason check that treats a
  `rst:0x… (…WDT…/BROWN…/PANIC…)` banner as both a boot and a crash. A clean
  `POWERON` / `SW_CPU_RESET` is not a crash.
- *Strand consistency* — neutral shapes only: a line naming a strand/output/
  channel from which an index, a pixel count and a `type:` token are EXTRACTED.
  The check compares the extracted counts against the plan's own expectation; a
  count that is not the expected one is reported as the firmware-default-strand
  suspicion (a FAIL), while "no strand line recognized" is inconclusive (a note,
  not a pass). No private-firmware wording is embedded anywhere; exact local
  patterns can be supplied at run time through the gitignored file named by
  `BM26_HIL_SERIAL_PATTERNS` (JSON `{"crash": [...], "strand": [...]}` — a
  named-but-missing file is a loud failure, never a silent skip).
- *Unstamped lines* — a capture line without a parseable ISO stamp breaks the
  helper's contract. It is counted (`malformedLines`) and still scanned for crash
  markers (a crash must never hide behind a formatting slip), but it cannot be
  placed in time so it delimits no boot.

**Expected boots are derived from the device's own reply, not assumed.**
`{outcome:"needs-reboot", reboot:true}` or a lost reply ⇒ expect exactly 1 boot
and wait out the reboot; `{outcome:"applied"}` ⇒ expect 0 boots and read back
immediately. Anything else is D2 — a hard failure quoting the device. See
deviation 1.

**Safety.** The allowlist gate and the flag gate both run before any I/O, both
raise `UsageError`, and both exit 2 with the usage block. The runner speaks
device HTTP `:80` (through the client) and the named COM ports only; a `--board`
carrying a port or a hostname is refused by `lastOctet`, so a sim/engine port
cannot be typed in. Snapshots go to
`~/tmp/led_controller_configs_backup/hil_<id>_<stamp>.json` through a 6-line local
writer; serial logs to `~/tmp/hil_serial/<controllerId>_<stamp>.log`. Both trees
are gitignored and neither is ever pasted into a tracked report.

**Abort semantics.** A leg failure is board-confined: the remaining mutating legs
for that board are skipped, RESTORE is attempted anyway, the board is marked FAIL
regardless of restore success, and the next target still runs. An allowlist,
preflight, serial-attach or transport-level failure is a global abort — the loop
breaks after restoring what was written. RESTORE runs only when something was
actually WRITTEN; a preflight/snapshot/plan refusal wrote nothing and gets a SKIP
row instead of a gratuitous write.

## 5. Deviations from `_363` §6

1. **Expected boots follow the device's reply instead of a flat "one boot".**
   §6.3 says the config leg asserts EXACTLY ONE boot. But §2.1 also pins that an
   identical body answers `{outcome:"applied"}` and changes nothing — and the
   config leg's body is derived from the board's own snapshot, so a healthy
   idempotent re-assert may legitimately not reboot at all. Asserting a flat 1
   would fail a green board. The runner therefore expects 1 boot when the device
   said `needs-reboot`/`reboot:true` or the reply was lost, and 0 when it said
   `applied`. "More boots than asked for" stays a FAIL in both cases, which is
   the crash-loop class §6.3 exists for. The toggle legs are genuine state
   changes and expect 1 each.
2. **The restore body is `{strands, dmx}` only — `deviceName` is never
   restored.** §6.4-4's parenthesis reads both ways; the second half ("an
   originally-invalid stored name stays repaired and is REPORTED") is the one
   that is physically possible: the repair only ever fires when the STORED name
   was invalid, and the firmware rejects every write carrying an invalid name, so
   writing it back cannot succeed. The runner leaves the repaired name and prints
   a `⚠ deviceName was REPAIRED …` line. Test-pinned.
3. **`--expect-universes` is refused with more than one target.** The flag as
   specified states ONE list of universes, and the two authorized boards carry
   different ones. Applying one list to both would either be wrong or silently
   partial, so it is a usage refusal telling the operator to run one target at a
   time.
4. **`--skip-config` together with `--skip-toggle` is refused** — it would run a
   snapshot-and-restore cycle that proves nothing while still writing to a board.
5. **The informational swarm note rides the CONFIG read-back row** (as
   `_365` designed it — `swarmEnabledNote` is a separate export, never a
   mismatch).
6. **Column layout is §6.5's shape, not byte-identical to its sample.** The
   per-leg note reads `11.2 s, responseLost=false, boots=1, strands on serial:
   2×40 ✓`; the sample split the strand fact onto the verify row. Same facts,
   same rows, same verdict line.

## 6. What the sanctioned S6 run needs from the operator

1. **Announce first.** Both boards reboot several times and go dark briefly while
   the live stack streams to them (§7 of `_363`).
2. **Identify the COM ports**: `python tools/hil_serial_tail.py --list` from
   `simulation/`, then map each board to its port. The listing prints device,
   `VID:PID`, description and serial number; ESP32-S3 native USB and the common
   UART bridges are recognizable. MAC-based identification is deliberately NOT
   offered — reading a MAC over serial resets the chip into its bootloader.
3. **pyserial must be installed** (`pip install pyserial`) — the helper crashes at
   import otherwise, by design.
4. **Both target ports must be free** — another terminal holding COM7/COM8 makes
   the attach gate abort before any write, which is the intended behaviour but
   costs a run.
5. **Time the run while the smokestack swarm is idle** (`_363` §10.4): both
   targets are followers of a swarm whose persistent leader is one of the
   off-limits boards. The runner never sends a swarm command, but a leader-driven
   sync mid-run would surface as a loud HTTP/serial mismatch.
6. **Invocation** (the only shape that works — no defaults exist):

   ```text
   node tools/hil_push_check.cjs \
     --board <.65 IP> --expect-id ss_right_right --serial ss_right_right=COM? \
     --board <.66 IP> --expect-id ss_right_left  --serial ss_right_left=COM?
   ```

7. **Evidence to collect into the S6 bundle**: the full PASS/FAIL table
   transcript, both snapshot paths, both serial log paths plus the per-leg
   summarized serial verdicts (boot counts, the zero-crash statement, the
   strand-check result), and before/after `configHash`. Raw serial logs stay in
   `~/tmp` — never pasted into a tracked report.

## 7. Open gaps

- **The run body itself is unexercised.** Every pure helper is mock-gated, but
  the leg orchestration, the child-process handshake with the capture helper and
  the abort/restore paths have only been read, not run — by the slice's own
  safety rule. The first real execution is the S6 operator-announced run; treat
  its first minutes (preflight + snapshot + the CONFIG leg) as the smoke test.
- **The strand expectation assumes one pixel count across the enabled outputs**
  (`plan.assignments[0].pixelCount`). True for both targets today (2×40 px). A
  board with mixed counts would produce strand-check notes that need reading, not
  a wrong verdict on the HTTP side.
- **The strand heuristics are generic by construction.** Until
  `BM26_HIL_SERIAL_PATTERNS` is pointed at a local pattern file, a firmware whose
  boot lines do not contain the word strand/output/channel plus a count will make
  the strand check *inconclusive* (a note). Boots and crash markers do not depend
  on it.
- **`--gamma` is not built** (`_363` §11 + `_364`): gamma is out of the runner
  entirely this wave.
- **No `docs/` change** — S4 (`_367`) owns the documentation surface; the HIL
  tooling is referenced only from `_363` and this report.

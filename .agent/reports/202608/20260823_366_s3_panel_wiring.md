# 366 — S3: panel wiring (identity gate, narrowed copy, sync chip, DMX ⏻ toggle)

Implements slice **S3** of `_363` (§2.3-1/2/3, §3, and the §5 test blocks for
`per_output_push` / the UI suite / the panel-sync cases), on top of `_364` (S1)
and `_365` (S2). Everything here is implemented and gated (`node --check`,
targeted `node --test`, greps). **No git operation, no device contact, no stack
bounce, no live-stack port bound, no browser launched.**

Controllers are named by `controllerId`; test fixtures use private/documentation
-range IPs only.

---

## 1. Objective

Wire the narrowed contract S2 landed into the Controllers panel: refuse a write
to a board the card is not bound to, tell the operator the narrowed truth in the
push dialogs, stop calling a swarm board "drift", surface the non-failing swarm
note on push outcomes, and add the one-button DMX ⏻ toggle. Docs (S4) already
describe this surface; this slice makes the panel match them.

---

## 2. Changes — `simulation/src/gui/led_discovery_panel.js`

### 2.1 Pre-write identity gate (§2.3-1)

New PURE export `identityGateRefusal(controller, status)` → the refusal sentence
or `null`. A card is gated only when it is BOUND (`device.controllerId`); an
unbound card claims no identity and pushing it is still how it binds. The
sentence names BOTH ids, the IP, and states that nothing was written; a box that
answers with no `controllerId` at all is refused too ("no controllerId").

Three call sites, all BEFORE any body exists:

| Path | Behaviour on refusal |
|---|---|
| `startPush` (single ⬆ Push) | after the snapshot+status reads, **before the dialog**: loud toast + `▲ Drift` chip carrying the same sentence; the confirm dialog never opens |
| `pushAllLedControllers` (per controller, right after its `getStatus`) | that board is `failed` with the sentence as its detail + its own progress line; **the loop continues** |
| `toggleDmx` | refuses before the snapshot read, so no body is ever built |

`startPush` is now exported — the gate has to be provable to refuse before a POST
exists, and that proof needs the real entry point.

### 2.2 Warning copy (§2.3-2)

`FORCE_PUSH_WARNING` / `FORCE_PUSH_ALL_WARNING` rewritten to the plan's binding
text verbatim (`45 s` interpolated from `REBOOT_WAIT_TIMEOUT_MS`, as before) and
now **exported**, so the copy is asserted in one place (the same rule the
sync-chip tooltip already follows). The `_362` promise *"A board in SWARM mode
leaves SWARM mode"* is gone from both; the new clause **"Strand type, color
order, swarm and gamma settings are NOT touched."** replaces it. Push-all keeps
its pluralized form and its trailing sequencing sentence.

### 2.3 Sync chip (§2.3-3)

`computeSyncState` keeps the full-array mapping compare and the
`snapshot.dmx.enabled !== true` drift clause (detail now "board is not DMX-driven
— push will force DMX ON"). The `swarm.enabled === true → drift` clause is
**removed**: the narrowed push never mentions swarm, so a swarm board with a
correct mapping and DMX on would be pushed with zero change — claiming drift
there promises a change the push cannot make. Zero new reads; no `snapshot.swarm`
read remains anywhere in the panel.

### 2.4 The DMX ⏻ toggle (§3)

- **Control**: every LED card renders `⏻ DMX: ?` / `⏻ DMX: on` / `⏻ DMX: off`
  between ⬆ Push and Re-bind, disabled with "set the device IP first" when the IP
  is unusable. **No confirm dialog.** Tooltip carries the plan's sentence
  ("writes the board's DMX flag and reboots it (~11 s)") plus what THIS click will
  do and what is not written.
- **Label model**: new PURE export `dmxToggleModel(ctx, controller)` — label,
  click target, class and tooltip from the last-confirmed observation. From `?`
  the click asks for **ON** (the state a show needs, and the same one the push
  forces); a known state offers its opposite.
- **State store**: `dmxStateCache`, a scene-scoped Map exactly like `syncCache` /
  `liveMacCache` (G7), written ONLY from reads the panel already performs —
  `computeSyncState`'s sweep, `startPush`'s snapshot, the push-all snapshot, the
  push read-back verify, and the toggle's own two read pairs. **No polling, no
  timer, no TTL, no sweep, nothing persisted into the scene.** Exported getter
  `getDmxState`; a failure deletes the entry so the label falls back to `?`.
- **Flow** `toggleDmx(ctx, controller, targetEnabled, io, button)`: identity gate
  → one `getStatus`+`getConfig` → `buildDmxToggleBody` → `pushDmxToggle` →
  (`needs-reboot` or a LOST reply) `awaitReboot` → `getStatus`+`getConfig` →
  `diffDmxToggle` → label + toast. Phase text on the button: `⏻ reading…` →
  `⏻ writing…` → `⏻ rebooting…` → `⏻ verifying…`. Same arbitration as the push:
  an unanswered write is ambiguous and settled by the read-back; an ANSWERED
  non-2xx (400, the staged-config 409, anything else) is a definite loud failure;
  an outcome that is neither `applied` nor `needs-reboot` is a hard failure
  quoting the device (D2). Every failure = loud toast + label `?`.
- **NOT built** (anti-switch checklist honoured): no fleet toggle, no status
  sweep, no DMX⇄SWARM mode model, no swarm write, no save-server route
  (browser-direct like the push), no scene persistence of the live mode.

### 2.5 The informational swarm note (§2.2 rendering)

`pushPerOutputVerifyRecord` computes `swarmEnabledNote(verifyConfig)` from the
read-back it already has and returns it as `swarmNote`. `runPerOutputPush`
appends it to the outcome line (`… · ℹ board also reports SWARM enabled — …`)
without touching `outcome.ok`; `pushAllLedControllers` appends it to that board's
`detail`, beside the lost-reply and shared-address notes, so it shows on the
results table row while the row stays `PUSHED`.

### 2.6 `simulation/style.css`

New `.led-device-dmx-toggle` + `.led-dmx-on` / `.led-dmx-off` /
`.led-dmx-unknown` (ok tint / secondary / muted-dashed), built on existing theme
vars — no new tokens, no `.led-push-*` or gamma rule touched.

## 6. Deviations from the plan / brief

1. **Label string is `⏻ DMX: on` (etc.), not bare `DMX: on`.** `_363` §3 asks for
   a "`DMX ⏻` control … labeled from last-confirmed state"; docs/41 §4.4 writes
   the states as `DMX: on / DMX: off / DMX: ?`. The rendered label carries both:
   the ⏻ affordance and the state. Doc §4.4 stays true in substance; if the
   operator wants the glyph dropped it is one constant.
2. **A fourth phase string, `⏻ reading…`**, precedes the plan's three. The
   pre-write read pair is a phase the operator can be sitting through; leaving it
   unnamed would be the "hang or working?" ambiguity the phase text exists to
   kill.
3. **`getStatus` runs before `getConfig`** in the toggle (docs/41 §4.4 lists the
   pair in the other order). The identity gate needs the status first and must
   refuse before a snapshot is read; still exactly one read of each.
4. **`toggleDmx` takes an optional 5th `button` argument** beyond the brief's
   4-arg signature — the phase text has to land somewhere, and this keeps the flow
   DOM-free and testable (same pattern as `runPerOutputPush`'s `ui`).
5. **From `?` the toggle asks for ON.** The plan does not state the unknown-state
   target. ON is the show state and matches what the push forces; the flow re-reads
   the board before writing, so nothing is guessed about its current value.
6. **Three functions newly exported for the tests** — `startPush`,
   `showPerOutputPushConfirm`, and the two warning constants. No behaviour rides
   on the exports; they exist so the gate and the operator-facing copy are
   asserted at their real call sites.

## 2. The show — six stages, one thumb

```
GATHERING → PROCESSION → CEREMONY → THE KISS → CELEBRATION → PHOTO GLOW
```

| # | Stage | What fires | Rotation | Quick effects |
|---|---|---|---|---|
| — | **ARM** | Unchanged from Baby: `ev_prev` snapshot, autopilots disarmed, timeline lease taken. **Nothing on the rig changes until stage 1.** | — | — |
| 1 | `gathering` GATHERING | `wedding_gathering` | every 75 s, crossfade 3 s | VINTAGE WHITE · FLASH ALL WHITE |
| 2 | `procession` PROCESSION | `wedding_procession` | every 40 s, crossfade 4 s | VINTAGE WHITE |
| 3 | `ceremony` CEREMONY | `wedding_ceremony` **+ master fades to 0.55 over 6 s** — the surround recedes and the couple is the brightest thing left | every 120 s, crossfade 5 s | **none, deliberately** |
| 4 | `kiss` THE KISS (ceremonial) | two huge buttons. Both: master → 1.0 over 200 ms · FLASH ALL WHITE for 900 ms · the landing playlist at **+700 ms, under the flash**. `KISS → PARTY` lands `wedding_party`; `KISS → GLOW` lands `wedding_glow` | **off** (and a hard CUT — §5) | none |
| 5 | `celebration` CELEBRATION | `wedding_party` — a real action, so it starts the floor whichever way the kiss landed | every 45 s, `trans_flash` 400 ms | STROBE · VINTAGE WHITE · FLASH ALL WHITE · UV BLAST |
| 6 | `photos` PHOTO GLOW | `wedding_glow` + master → 1.0. Carries the FINISH affordance | every 90 s, crossfade 4 s | VINTAGE WHITE · FLASH ALL WHITE |
| — | **FINISH / ABORT** | Unchanged from Baby: `ev_prev` recalled as a 3 s morph, autopilots re-armed, lease released | — | — |

EXTEND is authored on all five holding stages (`RESTART GATHERING`,
`RESTART PROCESSION`, `MORE TIME`, `RESTART THE PARTY`, `RESTART GLOW`) —
manual stages, so all of them are action-extends.

**Two design choices worth naming.**

- **THE KISS is a CHOICE stage, like the reveal.** A wedding kiss has one
  outcome, but what happens *after* it does not: some rooms go straight to the
  floor, some want the champagne glow and the photographs first. The operator
  reads that about half a second before pressing, which is exactly the moment
  the two-button ceremonial UI exists for. Both variants share the identical
  flash; only the landing differs.
- **CELEBRATION is not a no-op hold.** Baby's `photos` stage fires nothing new
  because the answer playlist is already running. Here, `celebration` really
  activates `wedding_party` — which is a start if the kiss went to GLOW and a
  restart-from-the-top if it went to PARTY. Either way the button does what it
  says.

## 4. Colour, honestly — the one thing this show cannot fully control

The wedding wants gold, champagne and white. Two sources supply it:

- **The WHITE ONLY family (60–64) declares no `colorPalette1`/`2`.** The CPC
  only writes into exports a pattern actually declares, so the global palette
  and the colour autopilot **cannot tint them**. That is why `wedding_ceremony`
  (4 of 6) and `wedding_glow` (3 of 6) look right regardless of what the deck
  was doing before ARM. A test pins the majority.
- **Everything else takes the live global palette.** So GATHERING, PROCESSION
  and CELEBRATION are whatever palette is armed when the show is armed.

The show schema has **no palette verb**, and cannot get one cheaply: `globals`
takes finite NUMBERS, while `colorPalette1/2` are `hsv` objects in the
ParamCenter registry. So: **set a warm palette before ARM.** The closest shipped
pair is `phoenix` (c1 0.00 → c2 0.13, red→gold); there is no champagne/gold
palette in `config.yaml` today. See §8 for the follow-ups.

## 5. The finding that changed the show — THE KISS was dissolving, not cutting

Measured on the bench walk-through, first pass:

```
26174 ms  fire kiss(party)        (flash 0–900 ms, playlist authored at +700 ms)
31911 ms  deck actually lands wedding_party      ← +5.7 s
```

The runner applies a stage's `autopilot.transition` config to the deck **before
that stage's actions** (`special_events_service.js` → "The transition config is
applied BEFORE the actions"), and a stage that authors **no `autopilot:` block
at all inherits whatever the previous stage left set** — here, the ceremony's
5-second crossfade. So the 900 ms white flash was hiding nothing: the audience
would have watched a five-second dissolve out of the candle-lit ceremony into
the dance floor. That is the exact failure the flash-then-swap ordering exists
to prevent.

**Fix, entirely inside the show file:** `kiss` now authors
`autopilot: { active: false, transition: { enabled: false } }`. `active: false`
keeps rotation off (a ceremonial moment must never swap looks underneath
itself); `transition.enabled: false` is the real payload — it makes the swap a
hard CUT. Re-measured after the fix:

```
26167 ms  fire kiss(party)
26886 ms  deck lands wedding_party               ← +719 ms, under the flash
```

The cost is that the tab now draws a parked rotation card on THE KISS. That is
a fair trade for the moment landing correctly, and it is noted in the YAML.
CELEBRATION and PHOTO GLOW both re-establish a soft transition, so the cut does
not leak into the rest of the night — asserted in the test.

## 7. Two engine-side gaps found, deliberately NOT fixed here

Both belong to the special-events runner, which `_230` owns this wave. Neither
is caused by the wedding; the wedding simply steers around them.

1. **`globals` is not restore-covered.** The show schema offers a `globals`
   verb, but the special-event pre-show snapshot uses `captureLook()`, which
   records master + deck + overlays + mixGroups and **not** the shared
   ParamCenter bucket (`captureGlobalsForSnapshot()` exists and is used by
   PERFORMANCE MODE, but the special-event `captureSnapshot` dep does not call
   it). So a stage that pins SPEED would leave the night retuned after FINISH.
   Pinning SPEED for the vows would genuinely improve this show; it is not safe
   until ARM captures globals. The wedding uses only the three covered verbs
   and a test pins that.
2. **A stage with no `autopilot:` block inherits the previous stage's deck
   transition.** §5. Arguably the runner should reset the deck transition to a
   known default when a stage authors no block, rather than leaving the last
   one latched — otherwise every future show has to know this. Worked around
   in data for now.

## 8. Operator-tweakable choices (all one-line YAML edits)

1. **Show id / name.** File is `wedding_program.yaml`, id `wedding_program`,
   card name **"Wedding"**. Rename the file + `id:` together (they must match)
   if you want `wedding`.
2. **The KISS buttons.** `KISS → PARTY` / `KISS → GLOW`. Want one big button
   instead? The schema requires 2..4 `choices`, so replace the `choices:` block
   with the winning variant's `actions:` list; `ceremonial: true` still blacks
   out the rest of the column. Instructions are in the YAML.
3. **Stage words.** GATHERING · PROCESSION · CEREMONY · THE KISS · CELEBRATION
   · PHOTO GLOW. "FIRST DANCE" for stage 5, "VOWS" for stage 3, etc. — free.
4. **Palette.** Set a warm global palette before ARM (`phoenix` is closest).
   Adding a real `wedding_gold` / `champagne` pair to `config.yaml`
   `colorPalettes` is a good idea but lands in the deck-COLORS domain (`_224`),
   so it was left alone.
5. **Ceremony dim depth.** `masterFade target: 0.55`. Deeper is more intimate,
   shallower keeps faces lit for the photographer.
6. **Rotation cadences.** 75 / 40 / 120 / 45 / 90 s. All `shuffle: false`.
7. **Party transition.** `trans_flash` over 400 ms between party looks. Swap
   for `trans_crossfade` for a smoother floor, or `enabled: false` for hard
   cuts.
8. **Quick effects.** CEREMONY and THE KISS deliberately have none. That is a
   safety statement about flashing during vows, not an oversight.

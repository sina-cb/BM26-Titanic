**D-178-1 (LOW) — a stale entry can silently go live on a name collision.**
`gui_builder.js:5262-5271` clears casualties eagerly, so shrink/delete/rename can never leave a
resurrectable entry. But a stale entry created by a HAND EDIT (the only remaining origin — it is
warned as stale at every boot and save until then) silently becomes a live REVERSED flag the
moment a grow or a rename mints a fixture with exactly that name: nothing fires at the collision
moment — the stale warning simply stops and the exporter applies the flag to a light it was never
verified against. Scenario: operator hand-adds `Wall 5: reversed` while the group has 4 members
(typo for a different group), ignores the stale toast, later grows the group to 5 → member 5 is
exported REVERSED with zero notice. Severity LOW: needs a hand edit + an ignored standing warning
+ an exact name collision, and pattern 71 catches it physically. Cheap close (follow-up, not now):
in `generateGroupFromTrace`, warn when a NEWLY-CREATED member name already carries a store entry.

Minor, noted only: `pixelOrderFor` treats a hasOwnProperty-but-`undefined` entry as normal
(`pixel_order_store.js:87`) — unreachable from YAML, only a programmatic write could produce it,
and prune drops it.

## 3. Persistence integrity (Mechanism B) — CONFIRMED-CLEAN

- **Torn files: impossible by construction.** `writeBenchMirrorState`
  (`bench_mirror_state.cjs:384-404`) writes `<file>.tmp-<pid>`, `fsyncSync`s the fd, closes, then
  `renameSync`s. The rename is the commit point; a crash before it leaves the OLD file intact plus
  a `.tmp-<pid>` orphan that nothing reads (cosmetic; a robocopy would ship it harmlessly — it
  cannot arm anything).
- **Windows rename-over-existing: real.** Node's `fs.renameSync` on win32 is `MoveFileExW` with
  `MOVEFILE_REPLACE_EXISTING` — and it is not merely theory here: the state suite's
  write→overwrite→re-read round trips passed on THIS machine in my re-run. Residual failure mode
  is EPERM if the destination is momentarily locked (AV/robocopy); that throws into the ARM-site
  catch (`sacn_bridge.js:1985-1991`) → console.error + broadcastLog + `warnings[]`, arm unaffected.
  Loud, correct.
- **Version / unknown-key refusal: reachable.** Any parse/validation failure inside
  `readBenchMirrorState` is caught and surfaced as the `error` string (:354-373), which
  picker-open pushes into payload `warnings` (:1604) and the ARM-site read logs before rewriting
  (:1972-1977). Version is checked FIRST (:152), so a future layout says "this build reads v1
  only", not "unknown key".
- **Scene keying: structural.** The picker reads `sceneSelection(state, engineState.scene)`
  (:1605); the ARM write keys `setSceneSelection(…, verdict.sourceScene, …)` (:1978) where
  `verdict.sourceScene` is the LIVE engine scene the arm was proven against
  (`bench_mirror.cjs:511-519` — unreachable/sceneless engines are refused before it exists). The
  ARM path never reads the file for its selection at all — the client sends one — so there is no
  code path on which a `titanic` entry can act under another scene.
- **Stale-name refusal at ARM: real, and stronger than "refusal".** The ARM re-resolves the
  client's selection fresh (`sacn_bridge.js:1852`); a stale name dies on the resolver's
  UNKNOWN_SOURCE/INCOMPATIBLE refusals (`bench_mirror_resolve.cjs:700-710`) exactly like a
  hand-typed one. The state file cannot even reach that point uninspected: stale entries prefill
  nothing at picker-open (:1630-1644).
- **Cannot-arm guarantee:** `STATE_KEYS`/`SELECTION_KEYS`/`SLOT_STATE_KEYS` admit no key that
  could carry an arm bit, address, universe or host; tests assert against the exported sets.
